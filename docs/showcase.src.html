gphys円がたくさん、ぶつかり合う。速く、同じ結果で。

Goose で書いた、軽い 2D 物理エンジンです。円の剛体を、位置ベースの計算(PBD)と一様グリッドで動かします。ヒープ確保も外部ライブラリも使いません。同じ入力なら、いつも同じ結果になります。

10万個 17.0 ms/フレーム手書き C と 同じ速さ・同じ衝突数Node より 1.3〜1.7倍 速い総当たりより 10〜53倍 速い

HOW TO USE使い方

1世界を決める

箱の大きさと、マスの大きさ。マスは いちばん大きい円の直径以上にします。

gphys::world(0, 0, 100, 100, 1.0);
gphys::gy = -9.8;

2円を足す

位置・半径・質量。質量 0 は動かない物体(釘・壁)になります。番号が返ります。

let b = gphys::add(50, 80, 0.5, 1.0);
gphys::add(50, 20, 0.5, 0.0);

3進める・読む

1フレームを小ステップに分けて進め、配列から位置と速さを読みます。

gphys::step(1.0 / 60.0, 4);
print(gphys::px[b], gphys::py[b]);
// 設定(どれも ふつうの変数)
gphys::restitution = 0.3;   // はね返り 0〜1
gphys::friction    = 0.4;   // 摩擦: 小ステップごとに、ずれる速さを減らす割合
gphys::damping     = 2.0;   // 空気抵抗(1秒あたり)
// 便利な関数
gphys::explode(x, y, 届く半径, 強さ);   // 爆発で吹き飛ばす
gphys::is_free(x, y, r);              // そこに置けるか
gphys::reorder();                     // 物体をメモリでも空間の順に並べ直す(uid で追える)
gphys::state_hash();                  // 決定論の確認(対戦・リプレイの同期チェック)

CASES事例

4つの事例は examples/ にあります。どれも 3つの時刻を横に並べた絵です。動く円は、遅いとピンク、速いと黄色。紺は動かない物体です。

ゴルトンボード 動かない物体 3396 + 玉 2023

漏斗から落ちた玉が、釘にはじかれて左右に分かれ、下に正規分布の山を作ります。

使いどころ: パチンコ・ピンボール・抽選の演出

gphys::add(x, y, 0.45, 0.0);       // 釘(動かない)
if gphys::is_free(x, y, r) { gphys::add(x, y, r, 1.0); }
1フレーム 2.13 ms(6小ステップ)

群衆 敵 2000体 + 壁 69

四すみの敵が、丸い本拠地へ向かいます。向かう先はゲーム側が決め、物理は重ならないことだけを守ります。入口で渋滞が起きます。

使いどころ: タワーディフェンス・RTS・ゾンビの群れ

gphys::vx[i] += (dx / d * want - gphys::vx[i]) * 0.1;
gphys::step(1.0 / 60.0, 4);
1フレーム 0.66 ms ・ 10秒後に中へ入れたのは 42体

砂山 1200粒 × 2回

左に積んだ柱を崩します。左の2コマは摩擦 0、右の2コマは摩擦 0.4。摩擦があると流れが止まり、斜面になります。

使いどころ: 砂・豆・コイン・ガレキ

gphys::friction = 0.4;
粒の90%が入る幅: 摩擦0 → x=96 / 摩擦0.4 → x=48

爆発 玉 820

三角に積んだ山の下で爆発させます。中心に近いほど強く、重いほど弱く飛びます。

使いどころ: 爆弾・衝撃波・ノックバック

gphys::explode(50.0, 3.0, 14.0, 60.0);
448個を吹き飛ばした(直前・0.33秒後・4秒後)

SPEED性能

同じ場面(箱の半分を円で埋めて、重力で落とす)を、同じアルゴリズムの4つの実装で測りました。1フレーム = 1/60秒を4小ステップ。3回の中央値です。

17.0 ms10万個の1フレーム(Goose)。60fps の予算 16.7 ms とほぼ同じ
±9%Goose と手書きの C の差(以内)。衝突数は全部の規模でぴったり同じ
×535000個で、総当たり(O(n²))と比べた速さ。1000個では ×10

横軸・縦軸とも対数目盛り。点線は 60fps の予算(16.7 ms)。総当たりは 5000個までしか測っていません(1万個以上は遅すぎるため)。

測った場所: このクラウドのコンテナ・1コア・gcc 13.3(-O2)・Node 22.22。同じ機械で他の処理も動いているため、値は回ごとに1〜2割ぶれます。お手元の機械では未確認です。

WHY FAST速さのしくみ

  • 数え上げソートで整列: 小ステップごとに、円をマスの順に並べた作業用の配列へ集めます(O(n))。近い円が、メモリでも近くなります。
  • 調べるのは2区間だけ: 「同じマス+右のマス」と「下の行の3マス」は、どちらもメモリ上で続いた1区間になります。半分の近傍だけ見るので、同じ組を2回調べません。
  • 境界チェックをコンパイラに消させる: マスの区間を Goose のインデックス型 u32 upto sx にしたので、いちばん熱いループに配列の範囲チェックが残りません。
  • 相手だけメモリを読む: 円 a の位置はローカル変数に置いたまま、相手の区間を回します。これで衝突の計算が 2.6 → 1.6 ms(10万個・1小ステップ)になりました。
  • 確保ゼロ: ステップ中に、メモリの確保も移動も起きません。

LIMITSできないこと

  • 形は円だけ。回転・箱・多角形・関節はありません。
  • 深く積むと、少し揺れが残ります(2000個の山で、平均の速さ 0.2/秒)。小ステップを増やすと減ります。
  • 1スレッドです。
  • 物体を1つだけ消す関数はありません(reset() で全部消す)。
  • 決定論は、同じ機械・同じコンパイラで確かめました(gcc と TinyCC でハッシュ一致)。別の CPU どうしでの一致は未確認です。
